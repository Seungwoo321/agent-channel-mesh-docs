세션 설정을 만들기 **전에** 하는 일이다. 틀린 주소가 설정에 박히면 그다음은 전부 조용한 실패다 —
설정은 멀쩡히 만들어지고 메시지만 영원히 안 간다.

세션에서는 이렇게 시작한다.

```
메시 설정 도와줘
```

`mesh-setup` 스킬이 릴레이부터 묻고, 아래 두 툴로 확인한다. 사람이 주소를 짐작해 넣지 않는다.

## 로컬 — 내 에이전트끼리

`relay_check` 를 인자 없이 부르면 이 기계의 릴레이를 본다. 안 떠 있으면 **띄우는 명령
그대로**를 낸다. 세션이 백그라운드로 돌려도 되고 사용자가 붙여 넣어도 된다 — 같은 한 줄이다.

- 계정·저장소·토큰이 필요 없다. `127.0.0.1` 에 묶이므로 이 기계 밖에서는 닿지 않는다.
- 설정에 적을 주소는 `http://127.0.0.1:8787`.
- **세션보다 오래 살아야 한다.** 상대 에이전트가 붙어 있는 동안 끊기면 그쪽 메시지가 사라진다.
- 각 정상 세션은 resolver가 고른 자기 설정에 이 주소를 기록한다. 릴레이를 공유해도 신원·로컬
  저장소·receiver lease는 공유하지 않는다.

전체 절차는 [같은 기계 안에서](/guides/same-machine/).

## 배포됨 — 다른 사람과

**붙기만 할 때**는 주소를(릴레이가 요구하면 쓰기 토큰도) 운영하는 사람에게 대역 외로 받아
`relay_check` 에 `url` 로 넘긴다. 답이 없으면 거기서 멈춘다.

**직접 올릴 때**는 `relay_export` 가 배포할 디렉토리를 만든다 — 릴레이 번들 · `index.ts` ·
`vercel.json` · `package.json`. 그다음 명령을 툴이 그대로 내주고, 계정이 걸린 부분은 사용자가
직접 돌린다. 툴은 대신 배포하지 않는다.

전체 절차는 [다른 사람과](/guides/other-people/).

## 릴레이는 세션 설정에 하나다

채널은 여러 개를 둘 수 있지만 릴레이 주소는 세션 설정 전체에 하나다(`relay`). 로컬 릴레이와
공개 릴레이를 동시에 물릴 수는 없으므로, 옮길 때는 `relay_set` 으로 바꾸고 그 세션을 다시
연다. 다른 세션은 자기 설정으로 같은 릴레이를 계속 쓸 수 있다.

바꿔도 그 세션의 신원과 채널은 그대로다 — 릴레이는 봉투를 나르는 곳일 뿐이라 암호에 관여하지 않는다.
다만 옛 릴레이의 큐에 남아 있던 봉투는 따라오지 않는다.

## 세션당 receiver 하나

일반 MCP 어댑터는 설정된 릴레이를 폴링해 봉투를 복호화하고 세션 로컬 수신함에 쓴다. 같은
세션 설정에 어댑터를 두 개 띄우면 receiver lease 하나만 허용되어 두 번째가 `busy`가 된다.
실행 중 lease를 잃으면 `lost`로 표시된다. 오래된 프로세스를 종료하고 해당 세션을 다시 연다.
서로 다른 세션이나 PC가 같은 릴레이를 사용하는 것은 이 제한에 걸리지 않는다.

`channel_status`와 `dashboard`는 읽기 전용 관찰자다. 설정 멤버·서명된 TTL presence·session/
instance·`unmatched_presence`를 표시하지만 receiver lease를 잡거나 메시지 본문을 가져오지
않는다. 유효한 heartbeat만 `online`이고 없거나 만료되면 `unknown`이다.

## 세션 스케줄러와 릴레이는 별개다

`schedule_poll` 은 이미 로컬 저장소에 있는 수신함을 관찰하는 세션 로컬 Croner 작업이다.
릴레이에서 새 봉투를 fetch/post하지 않고 receiver lease도 잡지 않으므로, 릴레이 수신 루프를
대체하지 않는다. 스케줄러와 MCP 알림은 유휴 호스트를 깨우지 않으며, 저장된 메시지는 다음
턴에 `inbox`로 읽는다.

`channel_cleanup`은 스케줄러와 별개이며 현재 세션의 선택한 joined channel 로컬 기록만
미리 보고 정리한다. 릴레이 큐나 다른 세션의 수신함은 건드리지 않는다.
